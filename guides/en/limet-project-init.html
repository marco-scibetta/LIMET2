Project Init

Three columns, one spec-driven flow

LIMET keeps three views of the same project aligned: the documents in Qdrant, the code in Graphify, and the spec-driven methodology that ties them from the why to the test.

How it works

Qdrant · documents

The knowledge

Proposals, specs, plans, tests and decisions live as semantically-indexed markdown documents. Ask the project and Qdrant returns the most relevant chunks.

Graphify · code

The code tree

A knowledge graph extracts symbols, calls and dependencies from the source. Explain a node, find the path between two components, discover what a change impacts.

Spec-driven · method

Traceability

Every change starts from a proposal, passes through spec and plan, splits into tasks with mandatory tests, and closes only when verified and archived.

The documents LIMET produces

Generated by /limet-new in limet/changes/<date-slug>/, one per phase.

CHANGE_PROPOSAL.md

The why: problem, impact, capability.

SPEC.md

The verifiable what: requirements + given/when/then scenarios.

PLAN.md

The how at design level: approach, alternatives, risks.

TASK_LIST.md

Granular tasks with state, dependencies and test strategy.

TEST_PLAN.md

Unit + e2e, with quality self-review.

E2E_VERIFICATION.md

Step-by-step checklist for manual verification.

DECISIONS.md

ADR-lite: hard-to-reverse decisions.

TEST_EXECUTION.md

Real test outcome (from /limet-test).

BUG_REPORT.md

Structured bug with root cause and regression.

ARCHIVE_ENTRY.md

Summary of the archived work (from /limet-archive).

Init: what really happens

A single click on Register runs three steps in sequence.

1

register — registers the project in projects.json with root and docs path.

2

graphify extract — indexes the code into a knowledge graph (graphify-out/graph.json).

3

qdrant ingest — embeds the documents via Ollama and stores them in a Qdrant collection.

In Init you type the project name (a combo suggests the already-registered ones) and pick the docs path from the filesystem browser; the source path is derived as the parent of docs.

Re-index: realign the index

•

Incremental — re-embeds only changed files (default, skips unchanged).

•

Force — ignores the cache and re-embeds every file.

•

Clean (prune) — also removes chunks of deleted or moved files.

Re-index everything:

  • select workspace in the "Project" combo, leave "Docs path" empty. The workspace has registered all the docs (X\docs + X\module-a\docs + X\module-b\docs) → it re-indexes them all in one go.
  • If instead you put X (root) in the "Docs path" field, you index every .md under X (including limet/, code READMEs, etc.) — that's not what you want.

Rule: re-index everything = "Project" combo → workspace. Use the "Docs path" field only to index a specific folder on the fly.

Typical flow: Init once per project → work with the spec-driven cycle → Re-index when documents change and you want to refresh the Qdrant search.

Multi-module projects

Scenario: a folder X/ contains several modules (X/module-a, X/module-b) and a feature spans them. The setup is all done from the dashboard; the spec-driven work happens in the right Claude session.

The model

Workspace = X

The root folder. One Graphify graph (graphify extract X), one Qdrant collection (all docs, root + modules), one db. Shared infrastructure.

Module = limet/ only

Each subfolder of X has its own limet/ folder (local changes), but no Qdrant/Graphify/DB of its own: it shares them with the workspace.

Cross-module

A feature that touches several modules lives at X level and references the touched modules. A local feature lives in the module.

1

Register the workspace (Init). In Init: name = workspace, docs path = X\docs, and check "Workspace".

Under the hood, LIMET runs in sequence:

# ONE project, all docs in a single collection
register workspace --docs X\docs X\module-a\docs X\module-b\docs --root X
graphify extract X --code-only   # single graph of all modules
ingest --project workspace       # collection CRB_workspace (all docs)

No manual step: one click and the workspace is ready.

2

Verify in Projects. The Projects page lists workspace + modules with slug, root and docs paths. From here you see what is registered and what is not.

3

Cross-module feature. Open the Claude session in X (not in the module) and run /limet-new "cross feature". Documents go to X\limet\changes\<date-slug>\.

In PLAN.md / TASK_LIST.md list which modules it touches (e.g. module-a, module-b). For impact and dependencies between modules use Graphify: graphify path a b (relationship between two symbols) or graphify affected <symbol> (who is impacted).

4

Feature local to a module. Open the Claude session in X\module-a and run /limet-new "...". Documents go to X\module-a\limet\changes\: the change is tracked only in the module, not at workspace level.

Where things live

Cross-module change

X\limet\changes\<slug>\

Local change

X\module-a\limet\changes\<slug>\

Code graph

X\graphify-out\graph.json (single, all modules)

Qdrant collection

CRB_workspace — single, all docs

Config

config.yaml → a single projects.workspace entry

DB

single — Setup page, workspace project

Golden rule: if the change touches several modules, work in X; if it touches a single module, work in that module. Setup (Init/Re-index/Setup) is all from the dashboard; the spec-driven work (new/task/test/archive) happens in the right Claude session.

Linked projects (link between projects)

Two independent projects (A and B) that interact. Both initialized with LIMET: you want that, when working in A, Qdrant search also sees B's documents.

1

Initialize both. Register A and B with Init (or Init + "Workspace" if one is multi-module). Each has its own Qdrant collection.

2

Link them in Projects. Projects page → "Link projects" section: pick A and B, press Link. LIMET adds B's collection to A's (and vice versa).

3

Verify. In the Projects table you see the "Linked collections" column: A shows CRB_b, B shows CRB_a.

4

Work in A. When you query the project with cerebro_search, the search queries both A and B (primary collection + linked ones). Unlink with Unlink when no longer needed.

Current limit: the link concerns only Qdrant collections (document search). Graphify (code graph) and DB remain per-project: working in A you see A's graph and db, not B's. Cross-project graph/db is a future extension.
